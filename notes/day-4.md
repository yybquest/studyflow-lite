# Day 4: Agent Workflow, Planning & RAG

## 1. 学习目标

今天的重点是理解：

- Agent 不只是“回答一个问题”，而是一个多步骤工作流
- 为什么 agent 需要规划、判断和循环执行
- 什么是 workflow / orchestration
- RAG（检索增强生成）在 agent 中的作用
- 为什么工具、记忆和知识库通常要结合起来使用

## 2. 什么是 Agent Workflow

Agent workflow 指的是：

- 任务如何被拆解
- 模型如何在多个步骤中进行决策
- 什么时候调用工具
- 什么时候重新读取上下文
- 什么时候结束任务并给出结果

简单来说，agent 的能力不止于“生成一个回答”，而是要像一个小型流程引擎一样：

输入 → 理解任务 → 规划步骤 → 调用工具 → 收集结果 → 再判断 → 输出

这和单轮聊天的最大区别在于：

- 单轮聊天往往是一次性生成
- agent workflow 往往是多步执行

## 3. 为什么多步工作流很重要

很多真实任务都不是“一问一答”型的，比如：

- 读取一份文档并提炼关键结论
- 搜索资料并判断哪些信息可靠
- 比较多个方案并给出推荐
- 执行一个任务后再继续追踪后续动作

这些都需要 agent 具备：

- 任务拆分能力
- 状态追踪能力
- 结果判断能力
- 下一个动作的决策能力

因此，agent 往往需要一个 workflow，而不是一个直接输出答案的黑盒。

## 4. Single-step 与 Multi-step 的区别

### Single-step

适合：

- 简单问答
- 整理文本
- 生成简单总结

特点：

- 只有一个推理阶段
- 逻辑相对简单
- 不需要很多状态管理

### Multi-step

适合：

- 搜索 + 阅读 + 总结
- 执行脚本 + 检查结果 + 修正
- 多轮需求收集 + 调整方案
- 依赖外部资料的决策任务

特点：

- 步骤之间有关联
- 需要持续维护上下文
- 可能需要回溯和修正
- 更接近真实业务流程

## 5. Planning 与 Tool Calling 的结合

Agent 的一个典型动作链路是：

1. 读取用户要求
2. 识别当前任务目标
3. 判断是否需要检索/读取/计算
4. 调用对应工具
5. 结合工具结果重新推理
6. 决定继续下一步还是输出结果

比如：

用户问：

> 这份文档里提到了哪些关键问题？请先查找，再总结成列表。

agent 可能会：

- 搜索相关关键词
- 读取匹配的段落
- 提炼主题和关键点
- 最后输出结构化总结

这就是一个清晰的 workflow：

搜索 → 读取 → 分析 → 总结

## 6. 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种让模型在生成回答前先检索相关知识的方式。

它的核心思路是：

- 模型不是只依靠训练数据做回答
- 它先从外部知识库或文档中检索相关信息
- 再结合检索结果生成更符合场景的回答

### RAG 的典型流程

输入问题 → 检索相关文档 → 排序和筛选结果 → 把上下文喂给模型 → 生成答案

### RAG 的价值

RAG 可以帮助 agent：

- 结合私有知识
- 访问最新文档
- 减少幻觉问题
- 提升回答的可信度

对企业场景来说，RAG 非常重要，因为很多业务知识不在模型训练中，而在：

- 内部文档
- wiki
- Notion
- PDF / Word
- 代码库资料
- 客服记录

## 7. RAG 与 Agent 的关系

RAG 和 agent 不是互斥关系，而是相互增强的。

### RAG 解决什么问题

- “模型知道什么？”
- “哪些信息在当前知识库中？”

### Agent 解决什么问题

- “我应该怎么做？”
- “我需要调用什么工具？”
- “下一步应该走哪条路径？”

因此，一个强的 agent 通常会结合：

- Tools：让它做动作
- Memory：让它记住历史
- Context：让它有当前任务背景
- RAG：让它拿到相关知识

这四者共同决定了 agent 的“能力边界”。

## 8. 一个现实的例子

假设用户说：

> 我想知道这个项目中，哪些部分最关键，给我一个简洁的技术总结。

这时一个 agent 可能需要：

- 列出项目目录
- 找到主要代码文件
- 读关键文件
- 搜索关键模块和说明文档
- 结合资料生成总结
- 再用简洁语气输出结果

这个过程里，agent 不只是“生成文本”，而是在执行一个知识提取和分析工作流：

目录发现 → 文档搜索 → 内容阅读 → 信息提炼 → 输出结论

## 9. LangGraph 与 workflow 编排

Day 4 还会接触到一个非常典型的概念：workflow orchestration。

比如：

- 任务拆分
- 条件分支
- 步骤回退
- 循环执行
- 错误重试

这类设计适合复杂 agent。框架如 LangGraph 就是把 agent 的状态流转显式化的方式之一。它的核心思想是：

- 把状态放在 workflow 里
- 把节点视为“一个动作或一个步骤”
- 把边视为“下一步的条件”

这样就更容易管理：

- 任务的前后关系
- 多分支决策
- 复杂流程中的上下文流转

## 10. 为什么好的 workflow 让 agent 更稳定

如果没有良好的 workflow，agent 往往会：

- 直接输出不完整答案
- 不知道什么时候该调用工具
- 因为缺少状态而反复重复
- 在多轮任务中丢失关键上下文

而好的 workflow 能让它：

- 明确每一步目标
- 维持任务状态
- 知道两步之间依赖什么
- 在需要时重新获取信息

这也是 agent 真正“可用”的关键之一。

## 11. 我的学习总结

Day 4 让我理解到：

Agent 不是一个单一的聊天模型，而是一个会规划、会判断、会调用工具、会管理状态的系统。

真正强的 agent 经常具备以下能力：

- 能拆解任务
- 能决定下一步做什么
- 能在多步流程中持续追踪状态
- 能结合工具和知识库获取最有用的信息
- 能在对话过程中更新上下文和结论

RAG、Memory、Tools 和 Workflow 之间并不是孤立概念，而是相互补充的。

一个成熟的 agent，通常不是“一个模型直接回答”，而是：

“模型 + 工具 + 检索 + 状态管理 + 工作流编排”

共同协作完成任务。
